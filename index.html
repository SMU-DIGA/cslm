Position Paper · 2026

Language Models Demand New Computer Science

Language models are becoming the new universal computer. We argue they need their own theory — the Computer Science of Language Models (CSLM).

Traditional computer science gave us complexity theory, algorithms and formal methods for deterministic, operation-based machines. Language models break nearly every one of its assumptions: they generate tokens instead of executing operations, succeed with some probability instead of guaranteeing correctness, understand many modalities natively, and carry vast knowledge in their parameters. We can build ever more powerful models, but we cannot yet predict their behavior, explain their limits or guide their development from first principles.

CSLM is a theoretical and empirical framework for understanding computation by language models. It covers complexity analysis, algorithmic behavior, reliability, and how model architectures, training procedures and problem-solving capabilities relate to each other across modalities and tasks.

01Seven Fundamental Differences

Where language model computation departs from traditional computer science.

01

Generating–solving–verifying triad

Solve vs. verify→Generate, solve, verify

LMs can propose new problems, so the cost of generating a problem becomes something we can study.

02

Token as the basic operation

Operations→Tokens

The unit of computation is the token. Token count sets both cost and latency.

03

Unreliable reasoning

Deterministic→Probabilistic

LMs hallucinate even when prompted correctly, which makes verification both more important and harder.

04

Native multimodality

Pixels→Concepts

Text, images, audio and video share one representation space, so models reason about what they see and hear.

05

General-purpose capabilities

One algorithm per problem→One model

A single model translates, codes and proves, using internal "algorithms" it learned from data.

06

Training–inference stages

Inference only→Training + inference

Training plays the role of programming, but the link from data to behavior is indirect. Scaling laws are the first success story.

07

Inherent knowledge

Data-agnostic→Knowledge in weights

An LM is a knowledge base and a reasoning engine at once, and that knowledge can help or mislead its reasoning.

Goal

Complete tasks correctly with fewer tokens

Move LM development from empirical scaling to principled engineering, and understand both problems and models along the way.

02Token Complexity

A language model system (LMS) 𝓜 is made of one or more LMs. On a problem instance I, it uses τ tokens and succeeds with probability p. The aim is to minimize tokens while maximizing the success rate.

Definition · Token Complexity

Token complexity is a curve, not a single number: the set of achievable (tokens, success rate) pairs.

TC(I, 𝓜) = { τ(I, 𝓜, p) : p ∈ [0, 1] }
System & problem cards
SC(𝓜) gathers the token complexity of one system over all problems. PC(P) gathers it for one problem over all systems.
Asymptotic complexity
𝓜 solves P in O(f(n)) tokens at success rate p* if τout ≤ C·f(|I|) for all large enough instances.
LM-P & LM-NP
LM-P: solvable with poly(|I|) tokens at success rate ≥ p*. LM-NP: solutions verifiable with poly(|I|) tokens.
LM-Complete
A problem in LM-NP to which every LM-NP problem reduces token-efficiently. Is LM-P = LM-NP?

Why tokens, and not FLOPs?

Framework-agnostic

FLOPs per token change with the inference stack, for example with speculative decoding. Token count does not.

Observable

FLOPs are hidden for closed models. Token usage is always visible, and it sets cost and latency.

Structural

Tokens record how a model breaks a problem down, backtracks and elaborates, not just how much arithmetic it did.

03Connections to Existing Research

Token complexity gives existing lines of LM research a common language.

Scaling laws

Training laws over (N, D, C) may carry over to token complexity. Inference scaling, p ∼ (τout)β, is a direct trade-off between tokens and success rate.

Memory

Compare TC(I, 𝓜) with TC(I, 𝓜 ⊕ E). Retrieval spends tokens but can raise p. Self-evolving memory adds summarization costs.

Tools

Tools take heavy computation off the model. Building a tool pays off once its cost is spread over enough similar instances.

Multi-agent systems

Total cost depends on how the task is split, which model handles each part, and how much the agents need to communicate.

Fine-tuning

Treat "make 𝓜 solve P′ with success rate p" as the instance. TC then measures exploration cost and sample efficiency.

A first experiment

On sorting (n = 120), gpt-5-mini and gpt-5-nano trace clearly different curves: ≈110K vs. ≈280K tokens at 16 trials.

04Roadmap 2026–2030

Classical complexity theory took decades to mature. We propose five years for CSLM.

  1. 1936TuringTuring machine
  2. 1965EdmondsThe class P
  3. 1971CookCook–Levin theorem
  4. 1972Karp21 NP-complete problems
2026

Foundations & formalization

  • Standard conventions for counting tokens
  • Stable definitions of LM-P, LM-NP, LM-Complete
  • First lower bounds and benchmarks with instance generators
2027–2028

Classification & structure

  • Find LM-complete problems, or prove none exist
  • Reduction framework over 25+ problem classes
  • Extend to multimodal inputs and RL fine-tuning
2029–2030

Maturity & integration

  • Settle or characterize LM-P vs. LM-NP
  • Map the reliability cliff from p = 0.5 to 0.99
  • A universal token-complexity scaling law; CSLM-Bench

Open questions

  1. Hardness. What is the LM analogue of SAT? Are there problems that need exponentially many tokens to solve but only polynomially many to verify?
  2. Training. How should compute be split, C = Ctrain + Cinfer? How many tokens does it take to learn a new capability?
  3. Systems. When is it better to scale up parameters than to give a model memory, tools or other agents?
